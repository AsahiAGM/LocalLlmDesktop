# LocalLlmDesktop — AI-Driven Development Project Guide

## 1. この文書の目的

本書は、`ai_driven_dev` ブランチにおけるAI駆動開発の共通ガイドラインである。

本ブランチに関与するすべての開発AI、レビューAI、および人間は、本書を共通の前提として開発・評価を行うこと。

本書の目的は以下の3点である。

1. **開発方針の共有**：プロジェクトの目的、開発体制、現在の進捗、今後の方向性を共有する。
2. **成果物の評価**：ソースコードだけでなく、設計・処理の流れ・技術的判断の妥当性を評価できるようにする。
3. **継続性の確保**：開発AIやレビューAIが交代しても、これまでの経緯と判断を引き継げるようにする。

本書はプロジェクトの進捗に応じて更新する。実装状況と異なる記述を発見した場合は、実際のソースコードとテスト結果を優先し、本書の修正を提案すること。

---

## 2. プロジェクトの概要

### 2.1 対象プロジェクト

- プロジェクト名：LocalLlmDesktop
- GitHub：https://github.com/AsahiAGM/LocalLlmDesktop
- 開発対象ブランチ：`ai_driven_dev`
- 開発環境：Windows / Cursor
- 主な技術基盤：C# / .NET / Avalonia UI
- LLM実行環境：Ollama

※上記はこれまでに把握している情報である。正確なバージョンや構成は、作業開始時に対象ブランチの最新状態を確認すること。

### 2.2 プロジェクトの目的

既存のLocalLlmDesktopに音声入力・音声回答機能を追加し、音声による対話が可能なデスクトップアプリケーションを実現する。

既存のチャット機能を不必要に作り直すのではなく、既存資産を活用しながら機能を拡張することを基本方針とする。

### 2.3 AI駆動開発の実験目的

本プロジェクトは、単に音声機能を完成させることだけを目的としない。

AIを中心に要件定義、技術調査、設計、実装、テスト、レビューを進めることで、AI駆動開発の実用性と課題を検証する。

特に以下を評価対象とする。

- AIが自律的に課題を発見し、解決策を提案できるか。
- 技術選定や設計判断に十分な根拠があるか。
- 実装の品質と保守性を確保できるか。
- 人間による修正・追加指示をどの程度減らせるか。
- AIによる開発速度と、成果物の品質を両立できるか。

## 3. 開発体制と責任範囲

### 3.1 プロダクトオーナー（人間）

ユーザーが担当する。

主な責任：

- プロジェクトの目的と要求を提示する。
- AIから提示された選択肢や設計案を評価する。
- 要件・仕様・技術選定に関する最終判断を行う。
- 開発成果物が目的に合致しているか判断する。

AIからの提案を無条件に承認する必要はない。疑問点や判断材料が不足している場合は、追加調査を要求する。

### 3.2 主開発AI

Cursor上のGrokを主開発AIとする。

主な責任：

- 既存コードベースの調査
- 要件定義と技術調査
- 技術選定の提案
- アーキテクチャ設計
- 実装とテスト
- 不具合の調査・修正
- 開発状況と設計判断の文書化

単に指示されたコードを書くのではなく、要求を満たすために必要な作業を自律的に検討すること。

ただし、要求の解釈に重大な不確実性がある場合や、既存仕様を変更する場合は、判断を保留して確認を求めること。

### 3.3 レビューAI

ChatGPTおよびその他のレビューAIが担当する。

主な責任：

- アーキテクチャと設計の妥当性
- クラス間の依存関係と責任分担
- 処理フローとデータの受け渡し
- 例外処理・キャンセル処理・リソース管理
- セキュリティ・保守性・拡張性
- 要件と実装の整合性
- テストの妥当性と不足

レビューAIは、主開発AIの説明をそのまま正しいものとして扱わず、可能な限りソースコードやテスト結果から独立して検証すること。

### 3.4 レビュー結果の扱い

複数AIの意見が一致したことだけを根拠に、設計や実装を正しいと判断してはならない。

意見が異なる場合は、以下を比較する。

- 主張の根拠
- 技術的な前提
- 想定される利点と欠点
- 反例や例外
- 実際のコード・テスト結果との整合性

最終的な判断はプロダクトオーナーが行う。

## 4. 開発の基本原則

### 4.1 既存資産の活用

既存のコード、ライブラリ、フレームワーク、標準機能を優先的に調査する。

車輪の再発明を避け、成熟した技術を適切に活用すること。

ただし、既存技術を採用する際は、以下を確認する。

- 現在も保守されているか。
- プロジェクトの実行環境に適合するか。
- ライセンスや利用条件に問題がないか。
- 導入による依存関係や運用負荷は妥当か。
- 要求を満たすために必要な機能を備えているか。

既存技術を採用することと、その技術に無条件で依存することは同義ではない。

### 4.2 技術選定

技術選定では、少なくとも以下を検討する。

- 要件への適合性
- 実装・運用の難易度
- パフォーマンス
- 保守性
- 拡張性
- 外部依存関係
- ライセンスとコスト

採用案だけでなく、主要な代替案と不採用理由も記録すること。

### 4.3 既存機能への影響

新機能の追加によって、既存のチャット機能が不必要に変更されないようにする。

既存機能に変更が必要な場合は、変更理由、影響範囲、互換性への影響を明示すること。

### 4.4 不確実性の管理

未確認事項を事実として扱わない。

説明・報告では、以下を区別する。

- **確認済み**：ソースコード、実行結果、公式資料などで確認した事実
- **推論**：確認済みの事実から論理的に導いた内容
- **仮説**：検証が必要な予想
- **未確認**：まだ調査・検証していない事項

## 5. 成果物の評価基準

各フェーズの成果物は、以下の観点で評価する。

### 5.1 要件充足性

- 要求された機能を満たしているか。
- 明示されていない制約や例外を考慮しているか。
- 既存機能との整合性が保たれているか。

### 5.2 設計品質

- 各クラス・コンポーネントの責任が明確か。
- 依存関係が適切か。
- 不必要な密結合が発生していないか。
- 将来的な変更に対応できる構造か。

### 5.3 実装品質

- 処理が正しく実装されているか。
- 例外や異常系が考慮されているか。
- リソースの解放が適切か。
- キャンセルや非同期処理が適切か。
- コードの可読性と保守性が確保されているか。

### 5.4 テスト品質

- 正常系だけでなく異常系も検証しているか。
- 境界条件を考慮しているか。
- 既存機能への回帰がないか。
- テスト結果を再現可能な形で記録しているか。

### 5.5 開発効率

- 開発に要した時間
- 人間による追加指示の回数
- 人間によるコード修正の回数
- ビルド・テストの成功率
- AIが自発的に発見・解決した問題の数と内容

開発速度だけを重視して品質を犠牲にしないこと。

## 6. 設計・処理の説明規約

本プロジェクトでは、ソースコードを提示するだけでなく、設計意図と処理の流れを説明することを必須とする。

### 6.1 図の使い分け

実際の設計に適した図を選択する。すべての図を機械的に作成する必要はない。

| 図の種類 | 主な用途 |
|---|---|
| クラス図 | クラス、属性、メソッド、依存関係の説明 |
| シーケンス図 | オブジェクト間の呼び出し順序や処理の流れ |
| コンポーネント図 | アプリケーションの構成要素と境界の説明 |
| ER図 | データベースのエンティティと関連の説明 |
| 状態遷移図 | 録音状態や通信状態などの状態管理の説明 |
| フローチャート | 条件分岐を含む処理手順の説明 |

データベースを導入していない段階で、無理にER図を作成する必要はない。

### 6.2 説明すべき内容

設計・実装を報告する際は、必要に応じて以下を説明する。

1. その設計を採用した理由
2. 各クラス・コンポーネントの責任
3. オブジェクト間の依存関係
4. 処理開始から終了までの流れ
5. データがどのように受け渡されるか
6. エラー・キャンセル時の挙動
7. 代替設計と比較した利点・欠点

図とソースコードの内容が一致していることを確認すること。

### 6.3 図の表記

レビューや説明に使用する図は、読み手が構造や処理を追跡できることを優先する。

図だけで理解できない場合は、補足説明を付ける。

## 7. 現在の進捗と確認事項

### 7.1 確認できている事項

- `ai_driven_dev` ブランチを作成し、GitHubへPush済み。
- 本ブランチでAI主導型の開発実験を行う。
- 既存のLocalLlmDesktopを拡張対象とする。
- 音声入力・音声回答機能の追加を目指す。
- 既存アプリはOllamaとのHTTP通信を行うデスクトップアプリケーションである。

### 7.2 優先して解決する課題

**Ollamaの接続先がIPアドレスを直接記述する形になっている問題。**

現在の開発環境に依存した接続先を、アプリケーションのコードに直接記述していることが、環境の変更や配布時の問題につながる可能性がある。

まず、この問題の原因と影響範囲を調査すること。

調査・設計では、以下を確認する。

- 現在の接続先がどこで定義されているか。
- 接続先が固定されている理由。
- WindowsとWSL2のネットワーク構成との関係。
- 開発環境と配布環境で必要な接続方法の違い。
- 設定変更によって既存機能に生じる影響。

具体的な解決方式は、調査結果に基づいて提案すること。特定の方式を先に決めつけない。

### 7.3 未確認事項

以下は最新のソースコードを確認してから確定すること。

- 現在のディレクトリ構成
- 各クラスの責任と依存関係
- NuGetパッケージの正確な構成
- Ollamaとの通信処理の詳細
- 設定値の管理方法
- テストの実装状況
- 音声関連ライブラリの導入状況

過去の会話やREADMEの記載だけで、現在の実装状態を断定しないこと。

## 8. 今後の開発方針

当面の優先順位は以下とする。

1. Ollama接続先の直接記述に関する問題の調査と解決
2. 既存コードベースの全体把握と設計の文書化
3. 音声機能に関する要件定義
4. 音声認識・録音方式などの技術調査と選定
5. アーキテクチャ設計
6. 音声入力機能の実装
7. 音声回答機能の実装
8. 統合テストと最終検証

これは現時点での暫定的な順序である。調査結果や技術的な制約に応じて変更してよい。

各フェーズで、主開発AIは必要な調査・設計・実装手順を提案すること。

技術選定や設計方針を確定する前に、必要な根拠を提示すること。

## 9. 開発・レビューの運用

### 9.1 開発フェーズごとの報告

各フェーズ終了時に、少なくとも以下を報告する。

- 実施した作業
- 変更したファイル
- 変更理由
- 設計上の判断とその根拠
- 実行したテスト
- テスト結果
- 残っている課題
- 次のフェーズで行う作業

### 9.2 レビュー指摘の分類

レビュー指摘は、以下の分類を基本とする。

- **Critical**：重大な不具合、データ損失、セキュリティ上の問題
- **Major**：要件不充足、設計上の重大な問題
- **Minor**：保守性・可読性・例外処理などの改善点
- **Suggestion**：必須ではない改善提案
- **Question**：仕様や設計意図の確認が必要な事項

各指摘には、根拠、影響範囲、再現条件または該当箇所を付けること。

### 9.3 指摘への対応

指摘を受けたAIは、すべての指摘を無条件に受け入れる必要はない。

ただし、採用しない場合は理由と根拠を説明すること。

判断が難しい場合は、選択肢とトレードオフを提示し、プロダクトオーナーに判断を求める。

### 9.4 変更管理

- `main` ブランチに影響を与えないこと。
- 本実験の作業は原則として `ai_driven_dev` で行うこと。
- Git操作やファイル変更は、作業内容と影響を把握してから実施すること。
- 既存ファイルの削除や大規模な変更は、理由と影響を明示すること。
- フェーズごとに変更内容と検証結果を記録すること。

## 10. 共通の行動原則

本プロジェクトに関与するすべてのAIは、以下を守ること。

1. 不明なことを推測で確定しない。
2. ソースコードと実行結果を根拠として判断する。
3. 技術選定では代替案と不採用理由を検討する。
4. 既存の成熟した技術を調査し、不要な独自実装を避ける。
5. 実装だけでなく設計意図と処理の仕組みを説明する。
6. 問題を発見した場合は、原因・影響・解決案を整理する。
7. 他のAIの意見を鵜呑みにせず、独立して検証する。
8. 速度よりも、正確性・安全性・保守性を優先する。
9. 判断材料が不足している場合は、その不足を明示する。
10. 最終的な意思決定権はプロダクトオーナーにある。

## 11. 本書の更新

本書は固定された仕様書ではなく、プロジェクトの進行に応じて更新する共通ガイドである。

以下の場合は更新を検討する。

- 技術選定が確定したとき
- アーキテクチャが確定または変更されたとき
- 実装済み機能が増えたとき
- 重要な設計判断が行われたとき
- 開発体制や評価方法が変更されたとき

更新時は、実際のソースコードやテスト結果と整合していることを確認すること。

本書に記載されている計画と、実際の実装状態を混同してはならない。
