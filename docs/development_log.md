## 2026-11-26：Ollama接続先の外部設定化と単体テスト環境の整備

### 1. 実施目的

Ollamaの接続先URLがソースコード内に直接記述されている問題を解消し、実行環境に応じて接続先を変更できる構成にする。

あわせて、今回追加した接続先解決処理を継続的に検証できるよう、xUnitによる単体テスト環境を整備する。

### 2. 実施内容

#### 2.1 Ollama接続先の解決処理を実装

`OllamaEndpointResolver` を追加し、Ollamaの接続先URLを複数の設定元から解決できるようにした。

接続先の優先順位は以下のとおり。

1. 起動引数 `--ollama-base-url`
2. 環境変数 `LOCALLLM_OLLAMA_BASE_URL`
3. ユーザー設定ファイル `settings.json`
4. デフォルト値 `http://127.0.0.1:11434/`

上位の設定が存在する場合は、下位の設定より優先する。

設定値が明示されているにもかかわらず無効だった場合、下位の設定へフォールバックせずエラーとして扱う。

これにより、設定ミスが発生した場合に、意図しない接続先へ接続することを避ける。

#### 2.2 デフォルト接続先をループバックアドレスに変更

デフォルトの接続先を以下に設定した。

`http://127.0.0.1:11434/`

従来の開発環境固有のIPアドレスへの依存を解消し、アプリケーションとOllamaが同一のWindows環境で動作する場合の標準的な接続先とした。

なお、ループバックアドレスはアプリケーション自身が属するネットワーク環境を指すため、WindowsとWSL2など異なるネットワーク環境を跨ぐ場合は別途接続先の設定が必要となる。

#### 2.3 ユーザー設定ファイルの読み込み処理を実装

`UserSettingsStore` を追加し、ユーザーごとの設定ファイルから接続先を読み込めるようにした。

設定ファイルの形式：

```json
{
  "ollamaBaseUrl": "http://127.0.0.1:11434/"
}
```

設定ファイルの保存先：

- Windows：`%LOCALAPPDATA%/LocalLlmDesktop/settings.json`
- XDG_CONFIG_HOMEが設定された環境：`$XDG_CONFIG_HOME/LocalLlmDesktop/settings.json`
- それ以外の非Windows環境：`~/.config/LocalLlmDesktop/settings.json`

設定ファイルが存在しない場合は、未設定として扱う。

JSONの解析エラーやファイル読み込み権限などの問題が発生した場合は、エラー情報を返す。

#### 2.4 接続先URLの検証処理を実装

接続先URLについて、以下の検証を行う。

- 絶対URLであること
- スキームがHTTPまたはHTTPSであること
- ホスト名が存在すること
- URL末尾に必要なスラッシュを補完すること

不正なURLを受け取った場合は、接続先の解決に失敗したものとして扱う。

#### 2.5 アプリケーション起動時の接続先解決処理を変更

`App.axaml.cs` から接続先解決処理を呼び出す構成に変更した。

接続先の解決に成功した場合：

1. 解決されたURLを使用してHTTPクライアントを生成する。
2. `OllamaService` を生成する。
3. `MainViewModel` にチャットサービスを渡す。
4. アプリケーション終了時にHTTPクライアントを破棄する。

接続先の解決に失敗した場合：

1. `UnavailableChatService` を生成する。
2. エラー情報を `MainViewModel` に渡す。
3. 接続設定の問題をアプリケーション側で扱えるようにする。

これにより、接続設定の問題とチャット処理そのものを分離した。

#### 2.6 単体テスト環境を整備

`tests/LocalLlmDesktop.Tests` にxUnitを使用したテストプロジェクトを追加・整備した。

主な対応：

- xUnitのパッケージ参照
- テスト対象プロジェクトへの参照設定
- テストソースがアプリケーション本体のコンパイル対象に混入しないよう設定
- `InternalsVisibleTo` によるテストアセンブリからの内部メソッドへのアクセス許可
- テストコードへのxUnit名前空間の追加

## 2026-11-26 追記：STEP14 Ollama接続先Resolverの異常系設計と単体テスト拡充

### 1. 実施目的

Ollama接続先の解決処理について、設定元ごとに異なるエラー処理方針を明確化する。

特に、起動引数・環境変数の明示的な設定ミスと、ユーザー設定ファイルの読み込み・記述上の問題を区別し、適切なフォールバックと警告処理を実装する。

また、設計方針を単体テストで検証できる状態にする。

### 2. 実施内容

#### 2.1 接続先解決結果にWarningを追加

`OllamaEndpointResolution` に `Warning` プロパティを追加した。

これにより、接続先の解決結果を以下の3要素で管理できるようにした。

- `BaseAddress`：解決された接続先URL
- `Error`：接続先を解決できなかった場合のエラー情報
- `Warning`：フォールバックなど、処理は継続できるが通知すべき問題の情報

ErrorとWarningを区別することで、設定ファイルに問題があってもアプリケーションを起動できる構成とした。

#### 2.2 設定元ごとのエラー処理を明確化

接続先の優先順位は従来どおり維持する。

1. 起動引数 `--ollama-base-url`
2. 環境変数 `LOCALLLM_OLLAMA_BASE_URL`
3. ユーザー設定ファイル `settings.json`
4. デフォルト値 `http://127.0.0.1:11434/`

設定元ごとの処理方針を以下のように確定した。

| 設定元・状態 | 処理 | 結果 |
|---|---|---|
| 起動引数が有効 | 指定URLを採用 | Success |
| 起動引数が不正 | 下位設定へ進まず終了 | Error |
| 環境変数が有効 | 指定URLを採用 | Success |
| 環境変数が不正 | 下位設定へ進まず終了 | Error |
| 設定ファイルのURLが有効 | 指定URLを採用 | Success |
| 設定ファイルのURLが不正 | デフォルト値を採用 | Success + Warning |
| 設定ファイルの読み込み失敗 | デフォルト値を採用 | Success + Warning |
| 設定ファイルが存在しない | デフォルト値を採用 | Success |
| 設定ファイルのURLが未設定・空文字・null | デフォルト値を採用 | Success |

起動引数または環境変数が有効な場合、下位にある設定ファイルの問題は評価対象としない。

一方、起動引数や環境変数に明示的な不正値が指定されている場合は、設定ミスを隠さないため、デフォルト値へのフォールバックを行わない。

#### 2.3 Resolverの実装を変更

`OllamaEndpointResolver` において、設定ファイル由来のエラーを `Failure` ではなく、デフォルト値とWarningを持つ `Success` として返すように変更した。

また、設定ファイル内のURL検証には既存の `TryCreateBaseAddress()` を再利用した。

これにより、URL検証ロジックの重複実装を避けながら、設定元ごとの異常系を分離した。

### 3. 変更ファイル

|---|---|
| `Services/OllamaEndpointResolution.cs` | Warningプロパティを追加し、Success時にWarningを保持できるよう変更 |

| `tests/LocalLlmDesktop.Tests/OllamaEndpointResolverTests.cs` | 設定ファイルの異常系、優先順位、Warningの有無などのテストを追加・拡充 |

### 4. 設計上の判断

#### 4.1 ErrorとWarningを分離する

起動引数や環境変数は、利用者が明示的に指定した設定である。

その値が不正な場合、デフォルト値へ黙って切り替えると、利用者が意図しない接続先を使用する可能性がある。

そのため、これらの設定元では不正値をErrorとして扱い、処理を中断する。

一方、ユーザー設定ファイルは、ファイルの破損や記述ミスによってアプリケーション全体が起動できなくなることを避けるため、デフォルト値へフォールバックする。

ただし、問題が発生した事実はWarningとして保持する。

#### 4.2 設定の優先順位と短絡処理を維持する

上位設定が有効であれば、下位設定を評価する必要はない。

例えば、起動引数で有効なURLが指定されている場合、設定ファイルが破損していても接続先の解決には影響させない。

これにより、優先順位の高い設定が正しく指定されているにもかかわらず、使用されない設定ファイルの問題によって警告やエラーが発生することを防ぐ。

#### 4.3 URL検証処理を再利用する

設定元ごとにURL検証処理を実装すると、検証条件の不一致や保守コストの増加につながる。

そのため、既存の `TryCreateBaseAddress()` を共通のURL検証処理として利用する。

設定元による違いは、検証結果を受け取った後のエラー処理・フォールバック処理で表現する。

そのため、Warningの存在だけを理由にチャット送信を禁止しない。

#### 4.3 設定元の優先順位を維持

起動引数、環境変数、設定ファイル、デフォルト値の順序を維持する。

上位設定が有効な場合、下位設定の問題は評価対象としない。
